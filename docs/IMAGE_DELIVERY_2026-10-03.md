# ส่งภาพตามพื้นที่แสดง — 3 ตุลาคม 2569

## สิ่งที่ปรับ

ใช้ Image Optimization ของ Next.js ที่ติดตั้งอยู่แล้วและใช้ Sharp ภายใน ไม่เพิ่ม service หรือ dependency ใหม่ การ์ดของเรา/คู่แข่งและภาพย่อในตารางใช้ component `AdImage` ร่วมกัน

- การ์ดมี `sizes` และ `srcset` ให้เบราว์เซอร์เลือกขนาด ภาพย่อในตารางใช้ slot 48px และภาพคู่ที่เลือกในหน้าเทียบใช้ 90px
- ขนาดที่อนุญาต: 48, 96, 128, 256, 384, 512, 640, 960, 1280 และ 1600px เลือก WebP quality 85 หลังทดลอง quality 75/85/90 กับภาพชุดเดียวกัน ไม่ถือว่า quality ต่าง encoder เทียบกันได้
- เก็บ URL/ไฟล์ต้นฉบับเดิม หน้ารายละเอียดและภาพคู่แอดในพื้นที่เทียบยังเปิดต้นฉบับ วิดีโอ/ภาพโปสเตอร์ใน player คงพฤติกรรมเดิม
- การ์ดโหลดแบบ lazy และใช้แคชภาพของ Next ซ้ำ การแปลงเกิดครั้งแรกของขนาด/URL นั้น ไม่แปลงใหม่ทุกครั้งที่เปิดดู
- ภาพที่แปลงใช้การหมุนตาม orientation และไม่ขยายเกินต้นฉบับตาม pipeline ของ Next/Sharp สำเนาที่วัดไม่มี EXIF
- อนุญาต optimizer เฉพาะ HTTPS ของ Facebook CDN ไม่มี port/credentials/access_token ไม่ตาม redirect และไม่อนุญาต local IP แหล่งอื่นรวมถึง private signed archive ส่งตรงตามเดิม เพื่อไม่ให้ public optimizer cache ขยายอายุการเข้าถึงไฟล์ส่วนตัว
- ถ้า optimizer ล้มเหลว ลองภาพต้นฉบับก่อน ถ้าต้นฉบับเองเปิดไม่ได้จึงใช้สถานะสื่อเดิม ไม่บอกว่าสื่อต้นทางหมดอายุเพียงเพราะการแปลงผิดพลาด

รายละเอียดความสามารถและขอบเขตของ renderer: [Next Image documentation](https://nextjs.org/docs/app/api-reference/components/image) ตรวจคู่กับเอกสาร/implementation ของ Next 16.3.4 ที่ติดตั้งในโปรเจกต์

## ผลวัด

วัด 3 แอดจริงหลังการ resolve ภาพต้นทาง บนเดสก์ท็อป 1440×1000, DPR 1, กรอบการ์ดกว้าง 371px เบราว์เซอร์เลือกภาพกว้าง 384px

| ภาพ | ต้นฉบับ (bytes) | สำเนาที่ส่ง (bytes) |
| --- | ---: | ---: |
| 1 | 32,056 | 20,748 |
| 2 | 29,922 | 16,252 |
| 3 | 47,690 | 35,646 |
| รวม | 109,668 | 72,646 |

ลด bytes รวม **33.8%** ในตัวอย่างนี้ ต้นฉบับทั้งสามเป็น JPEG กว้าง 576/555/523px ไม่ใช่ไฟล์หลาย MB ผลนี้จึงไม่ใช่การประมาณว่าทุกแอดจะลดได้เท่ากัน และไม่ใช้แทนผลวัด LCP/Core Web Vitals ของผู้ใช้จริง

คำสั่งตรวจ: `node scripts/check-ad-image-delivery.mjs` ใช้บัญชีทดสอบที่เก็บไว้ในเครื่อง อ่านข้อมูลเดิม ไม่ซิงค์ ไม่เก็บ Apify ไม่เล่นวิดีโอ และไม่พิมพ์ signed URL/credentials ทดลอง encoder ก่อนเปลี่ยนเว็บได้ด้วย `--baseline`

หลักฐานอยู่ใน `test-artifacts/image-delivery/`: `baseline.json`, `optimized.json`, ภาพการ์ดเดสก์ท็อปทั้งสาม, `card-phone.png`, `card-phone-2x.png` และ `detail-original.png` ตรวจภาพที่แสดงจริงแล้ว การ์ดแสดงภาพครบในกรอบ ข้อความ UI อ่านได้ หน้ารายละเอียดใช้ต้นฉบับ จอ Retina เลือกพิกเซลเพิ่มตาม slot โดยไม่ upscale และการทดสอบเมื่อ optimizer โหลดไม่ได้ยังแสดงต้นฉบับได้

การเรียกภาพที่แปลงซ้ำทั้งสามได้ `x-nextjs-cache: HIT` ผ่านการทดสอบ URL/quality/width ที่ไม่อนุญาตตอบ 400 ชุดตรวจ host/SSRF 13 checks, focused ESLint, privileged-import check และ production build ผ่าน ตรวจ Flow 5 ขั้นของคลังเรา/คู่แข่ง/รายละเอียด/เทียบและมือถือผ่านด้วย `scripts/check-screenshot-flow.mjs` โดยไม่เริ่ม sync/collection

## ขอบเขต

AVIF ยังไม่เพิ่ม การแปลงภาพ private archive ล่วงหน้ายังไม่เพิ่ม และไม่ได้เปลี่ยนการ resolve ภาพผ่าน Meta หรือวิธีดึงผลลัพธ์จากฐานข้อมูล หากรอบแรกยังรอ Meta การลด bytes ไม่ได้ทำให้เวลา resolve นั้นหายไป วัดต้นเหตุส่วนนี้แยกก่อนเปลี่ยน pipeline เพิ่ม

การตรวจใช้เว็บ localhost รุ่นที่ build ใหม่ ยังไม่ได้ deploy รุ่นนี้ขึ้นระบบจริง
