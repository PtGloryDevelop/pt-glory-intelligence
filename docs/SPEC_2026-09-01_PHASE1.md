## Deterministic Formulas

| ชื่อ | สูตร |
|---|---|
| `collection_runs.collected_at` | `export.generated_at` |
| `ads.first_seen_at` | `MIN(collection_runs.collected_at)` ของทุก run ที่พบ `ad_archive_id` นั้น |
| `ads.last_seen_at` | `MAX(collection_runs.collected_at)` |
| `ad_age_days` | `current_date − ads.start_date` |
| Evergreen | `is_active = true AND ad_age_days >= config.evergreen_threshold_days` (**default 90**) |
| **Ads เริ่มรัน 30 วันล่าสุด** | `start_date >= current_date − 30` |
| **Ads ที่เราพบใหม่ 30 วัน** | `first_seen_at >= now() − 30 days` |
| Creative reuse | `collation_count > 1` · denominator = obs ที่ `collation_count is not null` |
| Format / CTA / platform / category distribution | group by ค่า พร้อม denominator ของแถวที่อ่านได้ |
| `dataset_quality.coverage` | `present_count / total_count` ต่อฟิลด์ต่อ dataset · **นับจาก observation ของ `dataset.collection_run_id` เท่านั้น** (I1) |
| quality tier | `>= 0.80` normal · `0.50–0.79` partial · `< 0.50` low |
### Frozen count formulas (ต้องตรงกับ collector เป๊ะ)

ถอดจาก `buildExportContract` ของ collector (`lib/core.js:541-570`) — **ห้ามตีความเอง** เพราะ semantics ที่ต่างกันจะทำให้ export ที่ถูกต้องถูก reject

```ts
const rows = [...export.ads, ...export.unresolved_ads];   // ลำดับนี้เท่านั้น
const withId    = rows.filter(r => Boolean(r.ad_archive_id));
const withoutId = rows.filter(r => !r.ad_archive_id);

computed_source_rows      = rows.length
computed_unique_ads       = new Set(withId.map(r => r.ad_archive_id)).size
computed_unique_pages     = new Set(rows.map(r => r.page_id).filter(Boolean)).size   // ★ ALL rows
computed_unresolved_count = withoutId.length
```

**จุดที่พลาดง่าย:** `unique_pages` นับจาก **ทุกแถวรวม `unresolved_ads`** ไม่ใช่เฉพาะ `ads[]` · `Boolean()` ใช้กติกา falsy ของ JS (`''`, `null`, `undefined`, `0` ถือว่าไม่มี) ตรงกับ collector

**ยืนยันกับไฟล์จริง:** reported 500/500/309/0 · computed 500/500/309/0 ตรงทั้ง 4 ค่า

### กติกาเมื่อตัวเลขที่รายงานไม่ตรงกับที่คำนวณ (I3)

| ฟิลด์ | ไม่ตรงแล้วทำอย่างไร |
|---|---|
| `source_rows` `unique_ads` `unique_pages` | **reject ทั้งไฟล์** พร้อมแสดงคู่ `reported` vs `computed` |
| `unresolved_count` | **reject** เช่นกัน |

เหตุผล: ตัวเลขไม่ตรงแปลว่าเราตีความไฟล์ไม่ตรงกับที่ collector ตั้งใจ ซึ่งเป็น conflict ตาม CLAUDE.md ที่ต้องหยุดและรายงาน ไม่ใช่เดาต่อ
ปรับเป็น warning ได้ภายหลังผ่าน `app_settings.count_mismatch_policy` ถ้าพบว่ามี divergence ที่อธิบายได้

**ห้ามแสดง `reported_*` หรือ `reported_quality_summary` บน UI ในฐานะตัวเลขของระบบ** แสดงได้เฉพาะในบล็อก provenance ที่ระบุว่ามาจาก collector

**ห้าม hard-code 90 กระจาย** — อ่านจาก `app_settings` ที่เดียว

## Core Invariants

**I1 — Dataset surfaces MUST be snapshot-consistent.**
เมื่ออ่านข้อมูลในบริบทของ Dataset ใด ๆ:
- mutable ad fields อ่านจาก `ad_observations WHERE collection_run_id = dataset.collection_run_id`
- mutable page fields อ่านจาก `page_observations WHERE collection_run_id = dataset.collection_run_id`

**ห้ามใช้ latest observation แบบ global ในบริบท Dataset** Ads Explorer ของ dataset และ Ad Drawer ที่เปิดจาก dataset นั้นต้องอยู่ใน snapshot context เดียวกัน

**I2 — Master current state เดินหน้าอย่างเดียว**
`first_seen_at = LEAST(...)` · `last_seen_at = GREATEST(...)` เสมอ
แต่ current-state fields (`is_active` `display_format` `publisher_platform` `page_ref` `collation_id`) อัปเดต **เฉพาะเมื่อ `incoming_run.collected_at >= existing.last_seen_at`**
การ import run เก่ากว่า → append observation ได้ แต่ **ห้ามทับ current master state**

-  ต่างกัน → master state สุดท้าย **ไม่ขึ้นกับลำดับ import**
-  เท่ากันเป๊ะและค่าขัดกัน → **run ที่ commit ทีหลังชนะ** (guard ใช้ ) — edge case ที่ยอมรับใน Phase 1
- ทั้งสองกรณี **observation ของทุก run ถูกเก็บครบ**
- ค่าซ้ำภายใน run เดียว → **first source occurrence ชนะ**

**I3 — ตัวเลขที่ collector รายงานคือ provenance ไม่ใช่ความจริง**
server ต้องคำนวณ `source_rows` `unique_ads` `unique_pages` `unresolved_count` เองจากข้อมูลที่ parse ได้จริง และ canonical data quality ต้องมาจาก server coverage calculator เท่านั้น

## Transaction Mechanism

**supabase-js หลายคำสั่งต่อกัน ≠ transaction** — ต้องเลือกกลไกจริงก่อนเขียนโค้ด

**เลือก: direct server-side Postgres transaction**
ใช้ driver `pg` ต่อผ่าน **Supabase transaction-mode pooler** ด้วย `DATABASE_URL` ที่เป็น server-only env

**บังคับ: หนึ่ง client ตลอด transaction**
```ts
const client = await pool.connect();          // จอง client เดียว
try {
  await client.query('BEGIN');
  ...ทุกคำสั่งใช้ client ตัวนี้เท่านั้น...
  await client.query('COMMIT');
} catch (e) {
  await client.query('ROLLBACK');
  throw e;
} finally {
  client.release();
}
```
**ห้าม** เรียก `pool.query()` แยกกันหลายครั้งแล้วเรียกว่า transaction — pool แจก connection คนละตัวได้ ทำให้ `BEGIN` กับ statement ถัดไปอยู่คนละ session และ `ROLLBACK` ไม่มีผล

เหตุผล:
- normalization อยู่ใน TypeScript ซึ่งเทสต์ได้ ไม่ต้องย้ายไป plpgsql
- รองรับไฟล์ใหญ่แบบ stream ทีละ batch ภายใน transaction เดียว
- ไม่ผูกกับขนาด payload ของ RPC argument

**ทางเลือกที่ปฏิเสธ**
| ทางเลือก | เหตุผลที่ไม่เอา |
|---|---|
| ยิง supabase-js หลายครั้งแล้วเรียกว่า transaction | **ไม่ใช่ transaction** ล้มกลางทางแล้วข้อมูลค้างครึ่ง ๆ |
| RPC ไป plpgsql function เดียวรับ JSONB ทั้งก้อน | atomic จริง แต่ payload 4.2 MB (และมากกว่านั้น) เป็น argument เดียวเปราะ และ normalization ต้องย้ายไป plpgsql หรือส่ง JSON ดิบเข้าไป ซึ่งเทสต์ยากกว่า |

**ผลข้างเคียงด้านสิทธิ์:** คอนเนกชันนี้ **bypass RLS** → ดูหัวข้อ Security

```
GET  /api/datasets/:id/ads     ?active&format&cta&platform&category&q&page&limit
  → { rows[], total, denominators:{...}, snapshot:{collection_run_id, collected_at} }
  ★ อ่านผ่าน snapshot ของ dataset.collection_run_id เท่านั้น (I1)

GET  /api/ads/:adArchiveId?datasetId=<uuid>
  → { master, snapshot_observation, observations[], context:'dataset'|'master' }
  ★ มี datasetId  → **ต้องยืนยันก่อนว่า ad นี้อยู่ใน `dataset_ads` ของ dataset นั้น**
                    ถ้าไม่อยู่ → **404** · ห้าม fallback ไป master state เงียบ ๆ
                    ถ้าอยู่ → mutable fields มาจาก observation ของ run นั้น (I1)
  ★ ไม่มี datasetId → คืน master current state และ **ต้องติดป้ายว่าเป็นสถานะล่าสุด ไม่ใช่ snapshot**
```

**I4 — snapshot API ห้าม fallback เงียบ**
การขอ ad ในบริบท dataset ที่ ad นั้นไม่ได้เป็นสมาชิก คือคำขอที่ผิด ไม่ใช่คำขอที่ต้องเดาให้ · ตอบ 404 เสมอ

**Dataset** — loading · ready · empty

## Data Quality Rules

คำนวณ coverage ต่อฟิลด์ต่อ dataset ตอน commit เก็บใน `dataset_quality`
ฟิลด์ที่ต้องวัด: `ad_archive_id` `page_id` `page_name` `page_like_count` `page_categories` `start_date` `display_format` `cta_type` `cta_text` `body_text` `title` `caption` `link_url` `link_description` `images` `videos` `cards` `collation_count` `publisher_platform` `is_active`

- `is_active = null` นับเป็น **ไม่ครอบคลุม** ไม่ใช่ false
- array ว่าง `[]` นับเป็นไม่ครอบคลุม
- object ที่ทุกคีย์เป็น null นับเป็นไม่ครอบคลุม (บทเรียนจาก `impressions_with_index` ของ Collector V2)

## Security / Authorization

RLS เปิดทุกตาราง · role `viewer` `analyst` `admin` อ่านจาก `public.user_roles`

| | viewer | analyst | admin |
|---|---|---|---|
| อ่าน business tables | ✓ | ✓ | ✓ |
| import / สร้าง category, dataset | ✗ | ✓ | ✓ |
| soft delete · settings · users | ✗ | ✗ | ✓ |
| อ่าน `audit_logs` | ✗ | ✗ | ✓ |

### เส้นทางสิทธิ์สองสาย — สำคัญเพราะ service role bypass RLS

| เส้นทาง | credential | RLS | การบังคับสิทธิ์ |
|---|---|---|---|
| **อ่านทั้งหมด** (dataset, explorer, drawer) | anon key + **user JWT** | ✅ ทำงาน | RLS เป็นด่านจริง |
| **import commit** | `DATABASE_URL` ฝั่ง server (elevated) | ❌ **bypass** | **ต้องตรวจ `requireRole('analyst')` ใน Node ก่อนเปิด transaction** |

กติกาบังคับ:
1. credential ที่ bypass RLS **ห้ามใช้กับ endpoint อ่านเด็ดขาด** — เส้นทางอ่านต้องผ่าน RLS เสมอ
2. ทุก privileged operation ตรวจสิทธิ์ใน Node **ก่อน** แตะ DB และเขียน `audit_logs` พร้อม `actor`
3. `DATABASE_URL` และ service-role key เป็น server-only env · **test ตรวจ client bundle ว่าไม่มีทั้งคู่**
4. RLS ยังต้องเปิดและถูกต้องอยู่ดี เป็นด่านที่สองสำหรับเส้นทางอ่าน ไม่ใช่ด่านเดียวของระบบ

### `current_user_role()` — helper กลางของ RLS

policy ทุกตารางต้องเรียกฟังก์ชันเดียวกัน ไม่ใช่ subquery ซ้ำ ๆ ที่หลุดง่าย

```sql
create function public.current_user_role() returns text
language sql stable security definer set search_path = public as $$
  select role from public.user_roles where user_id = auth.uid()
$$;
```

`security definer` จำเป็นเพราะ policy ของตารางอื่นต้องอ่าน `user_roles` ได้โดยไม่ต้องเปิดสิทธิ์อ่านตรงให้ผู้ใช้

**ผู้ใช้ห้ามแก้ role ของตัวเอง**
- `user_roles`: `select` ได้เฉพาะแถวของตัวเอง หรือทั้งหมดถ้าเป็น admin
- `insert` / `update` / `delete` ทำได้เฉพาะ `current_user_role() = 'admin'`
- policy ของ admin ต้องมีเงื่อนไข `user_id <> auth.uid()` สำหรับ `update`/`delete` เพื่อกัน admin ลดสิทธิ์ตัวเองจนไม่เหลือ admin และกัน privilege escalation ทุกรูปแบบ

- ไฟล์อัปโหลดถือเป็น untrusted — ไม่ eval ไม่ทำตามคำสั่งในเนื้อไฟล์
- `_pt_glory.request_url` เก็บได้ แต่ห้ามเก็บ cookie/token/CSRF ใดๆ ถ้าไฟล์มีมาให้ทิ้ง
- soft delete ด้วย `deleted_at` + policy กรอง

## Error / Partial States

แยกสองระดับเด็ดขาด

### File-level → reject ก่อน commit · **ไม่เขียน `import_quarantine` และไม่สร้าง `collection_run`**

| reason | trigger |
|---|---|
| `malformed_json` | parse ไม่ผ่าน |
| `schema_mismatch` | โครงไม่ตรง contract |
| `unknown_field` | พบ key ที่ไม่รู้จักในแถวใด ๆ |
| `unsupported_collection_method` | `collection_method` นอก enum |
| `size_limit_exceeded` | เกิน 5,000 records หรือ 25 MB |
| `count_mismatch` | `reported_*` ไม่ตรง `computed_*` (I3) |

ผลลัพธ์: API คืน 422 พร้อม `{reason, detail}` · ไม่มีอะไรถูกเขียนลง DB · บันทึกใน application log
**หมายเหตุที่ยอมรับใน Phase 1:** ไฟล์ที่ถูก reject จะไม่เหลือร่องรอยในฐานข้อมูล ถ้าต้องการประวัติการ reject ให้เปิด ticket แยกใน Phase 2

### Row-level → ไฟล์ valid แล้ว commit ปกติ · เขียน `import_quarantine`

| reason | trigger |
|---|---|
| `missing_ad_archive_id` | แถวใน `ads[]` ที่ `ad_archive_id` เป็น null |
| `unresolved_source_record` | ทุกแถวใน `unresolved_ads[]` |

แถวเหล่านี้ **ไม่เข้า `ads`** (คำตัดสิน B) · run มีสถานะ `partial` เมื่อ quarantine > 0

### อื่น ๆ

| กรณี | พฤติกรรม |
|---|---|
| import ซ้ำไฟล์เดิม | master เท่าเดิม · observation เพิ่ม · run ใหม่ |
| import run เก่ากว่า | append observation · **ไม่ทับ current state** (I2) · `first_seen_at` ขยับย้อนหลัง |
| DB ล้มกลางคัน | `ROLLBACK` ทุก write จริง ไม่มี run ค้าง |
| media URL หมดอายุ | Drawer แสดง placeholder ไม่พังทั้งหน้า |

## Acceptance Criteria

1. import ไฟล์ 500 ads จริง → `computed_unique_ads = 500`, `computed_unique_pages = 309`, quarantine = 0
2. preview ไม่เขียน DB (ยืนยันด้วย row count ก่อน/หลัง)
3. import ไฟล์เดิมซ้ำ → `ads` count เท่าเดิม · `ad_observations` เป็น 2 เท่า · run เพิ่ม 1
4. `first_seen_at` = `MIN(run.collected_at)` และ `last_seen_at` = `MAX(...)` พิสูจน์ด้วยการ import ไฟล์เก่ากว่าทีหลังแล้ว `first_seen_at` **ขยับย้อนหลัง**
5. **(I2)** import run เก่ากว่าที่มี `is_active` ต่างกัน → `ad_observations` ได้แถวใหม่ แต่ `ads.is_active` `display_format` `publisher_platform` `page_ref` `collation_id` **ไม่เปลี่ยน**
6. **(I1)** dataset A (run เก่า) และ dataset B (run ใหม่) ที่มี ad เดียวกันแต่ `is_active` ต่างกัน → Explorer และ Drawer ของ A แสดงค่าของ run A ส่วน B แสดงค่าของ run B
7. **(I3)** แก้ `unique_ads` ในไฟล์เป็น 499 → **reject** พร้อมแสดง `reported 499 / computed 500`
8. **(I3)** `dataset_quality` มาจาก server calculator · `reported_quality_summary` ไม่ถูกใช้เป็นตัวเลขของระบบที่ใดเลย
9. คอลัมน์ `likes/spend/reach/impressions` **ไม่มีอยู่ใน schema** และ normalizer ทิ้งคีย์เหล่านี้ — มี test
10. `is_active = null` แสดง `—` ไม่ถูกนับเป็น inactive และนับเป็นไม่ครอบคลุมใน quality
11. `page_categories` และ `publisher_platform` แสดงเป็น multi-value พร้อมข้อความว่ารวมกันเกิน 100% ได้
12. ไม่มี Sum ของ `page_like_count` ที่ไหนเลย
13. ฟิลด์ tier low (`title` `caption` `link_url` `link_description` `cards`) มี warning ทุกจุดที่ถูกใช้
14. viewer เรียก `/api/imports/commit` แล้วได้ 403 จาก server **ก่อนเปิด transaction**
15. Drawer เปิดขวาโดยไม่เปลี่ยน URL หลัก
16. ไฟล์ที่มี key แปลกหน้า → reject ทั้งไฟล์ พร้อมชื่อ key · **`import_quarantine` ว่าง และไม่มี `collection_run` ถูกสร้าง**
17. โยน error ที่ step กลางของ commit → **rollback ทุก write จริง** (row count ทุกตารางเท่าก่อนเริ่ม)

## Test Plan

**Unit** — validator (enum, unknown key, schema, size, count mismatch) · normalizer + forbidden-key stripper · coverage calculator (null-object, array ว่าง, is_active null) · ad_age / evergreen / started-30d / discovered-30d · count recomputation
**Integration** — commit transaction (**rollback จริงเมื่อ error กลาง step**) · upsert vs append · re-import idempotency · first_seen ย้อนหลัง · **I2: run เก่ากว่าไม่ทับ current state** · **I1: dataset สองรอบให้ค่าต่างกัน** · quarantine row-level vs file-level reject · RLS ต่อ role · **privileged route ปฏิเสธก่อนเปิด transaction**
**Fixtures** — golden: ไฟล์ 500 ads จริง (pin ไว้) · สังเคราะห์: unresolved ไม่ว่าง, unknown key, is_active null, collection_method ผิด, JSON พัง, ไฟล์ใหญ่ 5,000 rows
**E2E Playwright** — journey เต็มตาม User Journey
**Security** — client bundle ไม่มี service-role key · viewer ถูกปฏิเสธที่ server

## Rollback / Migration Notes

- ทุก migration มี `.down.sql`
- Phase 1 เป็น schema ใหม่ทั้งหมด ไม่มีข้อมูลเดิมให้ย้าย → rollback = drop ตามลำดับย้อนกลับ
- `import_quarantine` และ `app_settings` เพิ่มใหม่ ไม่กระทบตารางอื่น
- ถ้า collector เปลี่ยน contract อีก: เพิ่มค่าใน `collection_method` enum + migration ใหม่ **ห้ามแก้ normalizer ให้ยอมรับ key ใหม่เงียบๆ**

## ความเสี่ยงที่ยังเปิดอยู่

`schema_version` ไม่ขยับตาม contract → Phase 1 ใช้ `collection_method` แยก build แทน และ **reject ไฟล์ที่มี key แปลกหน้า** เป็นตาข่ายกันพลาด
ยังไม่มี source ของ collector ตัวใหม่ → ฟิลด์ที่ coverage ไม่ถึง 100% ถือเป็น optional ทั้งหมดในโค้ด
